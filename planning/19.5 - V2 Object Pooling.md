# Plan 19.5: V2 Object Pooling

## Overview

Entity pooling infrastructure for V2. Per-type pools as editor-placed children of CDGame. Pooled entities are reused across acquire/release cycles instead of being instantiated and destroyed. This plan modifies CDEntity and CDComponent2D (already updated in Plan 19 to reflect pooling) and introduces CDObjectPool.

**Depends on:** Plan 19 (all core infrastructure)
**Required by:** Spawners plan (first consumer of pools)

---

## Design Principles

1. **Pool reference IS the toggle.** `CDObjectPool` export on spawners. Null = instantiate fresh, non-null = acquire from pool. No separate boolean needed.
2. **Entity routes itself.** Callers always call `entity.deactivate()`. The entity checks `pool != null` internally — pooled entities return to pool, non-pooled entities are freed. Callers don't know the difference.
3. **Pool as parent.** Pooled entities live as children of their CDObjectPool node. This keeps the scene tree clean and has no impact on signal architecture (physics is spatial, `find_ancestor()` walks through pool nodes transparently).
4. **Separate acquire and activate.** Spawner acquires entity, configures it (position, velocity, etc.), then calls `activate()`. Entity is fully configured before it "wakes up."

---

## Signal Architecture Compatibility

Verified that pooled entities as children of CDObjectPool do not interfere with any signal pattern:

| Pattern | Mechanism | Pool Impact |
|---------|-----------|-------------|
| Entity ↔ Entity (physics) | Spatial collision layers/masks | None — physics is spatial, not hierarchical |
| Entity → Game bus (Announcers) | `CDGame.find_ancestor(self)` | None — walks through pool node to CDGame |
| Game bus → Entity (Controllers) | CDGroupRegistry queries by group | None — group membership is on entity, independent of tree |
| Entity ↔ Entity (non-physics relay) | Announcer → Dictionary → Controller | None — same path as above |

## What Gets Built

### CDObjectPool
**Type:** Node (editor-placed child of CDGame)
**Purpose:** Per-type entity pool. Pre-creates entities on `_ready()`, hands them out on `acquire()`, takes them back on `release()`.

**Key Exports:**
| Export | Type | Default | Description |
|--------|------|---------|-------------|
| `scene` | `PackedScene` | — | The entity scene to pool. Must be a CDEntity or extend CDEntity. |
| `initial_size` | `int` | `10` | Number of entities pre-created on `_ready()`. |
| `grow_by` | `int` | `5` | How many entities to add if pool is empty on `acquire()`. |
| `max_size` | `int` | `0` | Hard cap on total entities (active + available). 0 = unlimited. |

**Internal State:**
| Property | Type | Description |
|----------|------|-------------|
| `_available` | `Array[CDEntity]` | Entities currently in the pool (inactive, ready to acquire) |
| `_active` | `Array[CDEntity]` | Entities currently in play |

**Key Methods:**
| Method | Returns | Description |
|--------|---------|-------------|
| `acquire() -> CDEntity` | Entity or null | Returns an inactive entity from the pool. Does NOT call `activate()`. Returns null if pool is empty and at max_size. |
| `release(entity: CDEntity)` | void | Called by entity's `deactivate()`. Moves entity from `_active` to `_available`. Disables processing and visibility. |
| `get_active_count() -> int` | int | Number of entities currently in play. |
| `get_available_count() -> int` | int | Number of entities ready to acquire. |
| `get_total_count() -> int` | int | Active + available. |

**Startup (`_ready()`):**
1. For `initial_size` iterations:
   - Instantiate `scene`.
   - Set `entity.pool = self`.
   - Add as child (entity is under pool node in tree).
   - Entity runs `_ready()` → `_on_initialize()` (full lifecycle once).
   - Disable entity: `set_physics_process(false)`, `visible = false`, disable collision shapes.
   - Add to `_available`.

**`acquire()` flow:**
1. If `_available` is empty:
   - If `max_size > 0` and `get_total_count() + grow_by > max_size`: clamp `grow_by` to remaining capacity. If zero remaining, return null.
   - Instantiate `grow_by` new entities (same process as startup).
2. Pop from `_available`.
3. Add to `_active`.
4. Return entity. **Does NOT call `activate()`.** Caller configures entity, then calls `entity.activate()`.

**`release(entity)` flow:**
1. Remove from `_active`.
2. Add to `_available`.
3. Disable entity: `set_physics_process(false)`, `visible = false`.
4. (Collision shapes already disabled by `deactivate()` step 2.)

**`_exit_tree()` cleanup:**
1. All entities (active + available) are freed. Pool is gone.

## Changes to Existing Specs (Plan 19)

All of the following changes are **already reflected in Plan 19**. Listed here for reference:

### CDEntity — Pool-Aware Deactivation

`deactivate()` checks `pool != null`:
- **Pooled:** Calls `pool.release(self)`. Entity sleeps in pool.
- **Non-pooled:** `call_deferred("queue_free")`. Entity is destroyed.

`activate()` is a pool lifecycle method:
- Sets state to ACTIVE, enables collision/processing/visibility.
- Emits `"entity_activated"` — components re-initialize.
- Editor-placed entities are born active. Only pooled entities call `activate()`.

### CDEntity — Pool Reference

`pool` property (not exported — set by CDObjectPool after instantiation):
```gdscript
var pool: CDObjectPool = null
```

### CDEntity — Entity Bus Signals

| Signal | Description |
|--------|-------------|
| `"entity_deactivating"` | Components reset internal state, disconnect from game bus |
| `"entity_activated"` | Components re-initialize, reconnect to game bus |

### CDComponent2D — Pool Lifecycle Response

Components that need pool-aware behavior override `_on_entity_deactivating()` and `_on_entity_activated()`:

```gdscript
# In CDComponent2D base class:
func _ready():
    # ... existing setup ...
    if entity:
        entity.connect("entity_deactivating", _on_entity_deactivating)
        entity.connect("entity_activated", _on_entity_activated)

func _on_entity_deactivating():
    # Base: disconnect from game bus, stop processing
    set_physics_process(false)
    # Subclass overrides to reset internal state

func _on_entity_activated():
    # Base: reconnect to game bus, resume processing
    set_physics_process(true)
    # Subclass overrides to re-initialize counters, reconnect signals
```

**For non-pooled entities:** `_on_entity_deactivating()` fires, then entity is freed. `_on_entity_activated()` never fires. Components still clean up — they just don't get reused.

**For editor-placed entities:** These never call `activate()` or `deactivate()` during normal gameplay (they're born active). If a game reset reuses the same entity, `deactivate()` → `activate()` could cycle them, but this is an advanced pattern.

## Spawner Integration Pattern

Spawners use the pool reference as the toggle (Option C from design discussion):

```gdscript
# In any spawner:
@export var pool: CDObjectPool = null

func _spawn():
    var entity: CDEntity
    if pool:
        entity = pool.acquire()
        if entity == null:
            return  # Pool exhausted
    else:
        entity = scene.instantiate()
        get_parent().add_child(entity)
    
    # Configure entity (same regardless of source)
    entity.global_position = spawn_position
    entity.request_velocity_set(initial_velocity)
    
    if pool:
        entity.activate()  # Wake up pooled entity
```

Key points:
- `pool = null` → instantiate fresh, no pooling. Standard path for rare/special entities.
- `pool != null` → acquire from pool. Standard path for bullets, enemies, etc.
- Everything between acquire and activate is identical regardless of source.
- Spawners never call `deactivate()` — that's the entity's job, triggered by Arms/Goals/Marks.

```
├── CDCollisionBuffer

├── CDCollisionMatrix
├── BallPool (CDObjectPool, scene=ball.tscn, initial_size=3)
├── BulletPool (CDObjectPool, scene=bullet.tscn, initial_size=20)

│   ├── Brain_PlayerControl
│   ├── Leg_DirectMovement
│   └── Arm_GunSimple
├── CDEntity (Paddle_P2)          # Editor-placed, no pool
│   ├── Brain_InterceptorAI
│   └── Leg_DirectMovement
└── CDMark (LeftGoal)             # Area2D trigger zone
```

When Paddle_P1 fires, the spawner acquires from BulletPool:
```
BulletPool
├── Bullet_001 (ACTIVE, in play)
├── Bullet_002 (inactive, in pool)
└── Bullet_003 (inactive, in pool)
```

When Bullet_001 hits something and calls `deactivate()`:
- Returns to BulletPool's `_available` list.
- Processing off, invisible, collision disabled.
- Ready for next `acquire()`.

## Risks & Open Questions

1. **Memory overhead of pre-allocated pools:** An `initial_size=50` pool for invaders creates 50 entity trees upfront. For simple entities (few components), this is negligible. For complex entities, `initial_size` should be tuned per game. The pool doesn't allocate until `_ready()`, so games that don't place pool nodes pay nothing.

2. **Re-parenting alternative:** If re-parenting from pool to scene root and back is ever needed (e.g., for tree organization in debugging), the `acquire()` / `release()` methods would need `remove_child()` / `add_child()` calls. Current design keeps entities as pool children permanently. This can be added later without architecture changes.

3. **Pool warm-up on scene load:** All `initial_size` entities go through full `_ready()` → `_on_initialize()` on scene load. For pools with large initial sizes, this could cause a loading spike. Mitigation: keep `initial_size` conservative and let `grow_by` handle demand. Alternatively, a `warm_up()` coroutine could spread creation across frames — deferred to if/when it's a real problem.

4. **Thread safety:** Not relevant — Godot is single-threaded for scene tree operations. No consideration needed.
